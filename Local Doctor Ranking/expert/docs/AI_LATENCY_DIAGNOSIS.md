# DeepSeek latency diagnosis

Updated 6 October 2026, after the 17:50–17:51 UTC full-payload timing probe. **Tiny DeepSeek requests can be fast, while all three instrumented full-payload attempts failed to complete generation within the shared 15-second budget.** Delays are now visible both before response headers and after headers; their exact upstream cause remains unlocalized. No production provider setting or deadline was changed.

## Bounded live check

Exactly two generation requests were made, each containing only a synthetic request to return `{"ok":true}`. Neither professional records nor a private assessment brief was read or sent. Both used `deepseek/deepseek-v3.2`, temperature 0, reasoning disabled, strict JSON schema, streaming, at most 16 output tokens and a 15-second deadline. Both retained `require_parameters:true`, `data_collection:'deny'`, `preferred_max_latency:3` and maximum prices of $0.60 input / $1.70 output per million tokens.

| Request | Actual provider | HTTP headers | First content | Complete response | Tokens input / output | Reasoning tokens | Finish |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| Current automatic latency route | Alibaba | 896 ms | 897 ms | 1,249 ms | 23 / 8 | 0 | stop |
| Friendli only, fallbacks disabled | Friendli | 258 ms | 258 ms | 327 ms | 21 / 9 | 0 | stop |

Both returned HTTP 200 and complete event streams, with no processing-heartbeat delay observed. Recorded total cost: $0.0000414135. The unauthenticated endpoint-metadata request returned HTTP 200 in 191 ms. Sandbox networking separately failed with `EACCES`; the live diagnostic used approved network access, so that local restriction is distinct from upstream inference latency.

Friendli was chosen before either generation request from the [official model endpoint metadata](https://openrouter.ai/api/v1/models/deepseek/deepseek-v3.2/endpoints): it supported the required structured-output parameters, advertised $0.50/$1.50 per million tokens, and reported approximately 99.87% uptime over the preceding 30 minutes. Latency and throughput fields were null. This is not evidence that Friendli will always be faster, nor a recommendation to pin production after one observation. The automatic route selected Alibaba despite its differing metadata status; snapshot status is not a substitute for observed routing.

## Full-payload automatic-routing probe

The later diagnostic made exactly three generation calls using the three public-source professional verification briefs, real production explanation inputs and existing automatic OpenRouter latency routing. The SDK streamed internally only to collect timing; **no unvalidated wording was displayed**. Candidate ownership, strict output schema, the independent support-check requirement and the shared 15-second deadline were retained. No provider was pinned and no production code/configuration was changed.

End-to-end durations were 15,031, 15,012 and 15,008 ms respectively. All three attempts returned sourced fallbacks; **0/3 passed, and no independent checker was reached**. The adapter recorded `SyntaxError` on incomplete/empty assembled response text, with no finish reason or token usage available. That error name does not establish that the provider produced a complete but malformed answer. The small deadline overshoot is observation/cleanup overhead, not a longer generation allowance.

The artifact is `expert/.cache/model-automatic-streaming-verification.json`, generated by `evaluation/probe-streaming.cjs`, with AI code hash `776f983148141c819ec4586eff3acbf3ae1399f8b2c8f545f628ef9c24c490e8`. Its `expert-corpus-v1-b069c9a4afcfb76a2202` is the bounded public-source verification corpus, not the complete professional index. The actual route is known only for the first response; do not assign the other two attempts to Google or Friendli. A separate professional-payload Friendli-only experiment has not been performed.

## What the existing failures show

The public-source verification report contains one earlier fully verified pipeline response: generation 11.317 seconds plus independent support check 1.033 seconds, or 12.352 seconds overall. Other completed generations took 7.250–13.267 seconds and produced 249–632 output tokens. Several later calls exhausted the shared 15-second budget during generation; two earlier cases used the remaining budget in the support check.

The three short-ID verification calls and the subsequent JSON-object diagnostic all aborted during generation at approximately 15 seconds. Those non-streaming reports did not record response headers, first token or actual provider for failures. Their timing alone cannot distinguish upstream queueing, prefill/schema handling or slow output generation. Replacing JSON schema with JSON-object mode did not establish a fix.

The code makes two sequential model calls for a successful answer, sharing **one** 15-second abort signal. A first call that uses ten seconds leaves roughly five seconds for independent verification. `max_tokens` is an output ceiling, not a response-time guarantee. No retries are configured.

## Interpretation

- Persistent network failure, invalid credentials, universal model unavailability and universally broken strict-schema support are inconsistent with these two successful checks at this observation time.
- Strict schema itself is not universally slow: both tiny schema requests completed. The later full-payload probe is an end-to-end timing observation, not an experiment isolating schema overhead from prompt size or output generation.
- For full payloads, 3.664–10.081 seconds elapsed before headers. One response began content quickly after headers but did not complete; two produced no observed content before the deadline. This localizes the failure to the generation/upstream-response portion of the pipeline, not the independent checker, while leaving provider queueing, prefill, routing and output-generation causes unresolved.
- The two synthetic probes are not an end-to-end product acceptance test and do not clear the real-response release blocker. They differ from production in payload size, requested answer length and streaming transport. One sample per route provides no percentile estimate.

## Recommended next step, subject to discussion

The bounded full-pipeline timing probe above has now been performed. Preserve its three failed attempts and stop repeating the same payload merely to seek a passing result. A change to routing, payload size or generation architecture should be justified by a specific hypothesis and measured independently; the existing observations do not justify weakening the checker or presenting unverified streamed content.

If a further experiment is authorized, compare equal, entirely synthetic payloads at representative input/output sizes, with a fixed provider and one variable changed at a time. That would distinguish payload/decoding cost from routing variability more cleanly than the existing unpaired attempts. Provider pinning, prompt simplification or architectural changes should follow that evidence; none has been applied here.

The [routing documentation](https://openrouter.ai/docs/guides/routing/provider-selection) describes latency sorting as provider preference and `data_collection:'deny'` as a provider policy filter, rather than a latency guarantee or a comprehensive data-handling audit. The [streaming documentation](https://openrouter.ai/docs/api_reference/streaming) distinguishes gateway errors, processing comments and generated content; those distinctions are recorded in this diagnostic.

## Reproducibility and limits

`expert/evaluation/probe-synthetic-latency.cjs --live` is an opt-in, one-shot tool. It writes `expert/.cache/model-latency-synthetic.json` before requests, refuses to overwrite that report and hard-limits generation to two calls. The report contains timings, routing options and token metadata; it never stores an API key or authorization header. The existing report must be preserved rather than removed to trigger another run.

No application, patient-demo, source-normalizer, search or production configuration file changed for this investigation.

The later automatic-routing probe likewise retained its report rather than replacing earlier failures. Its three generation requests are additional to the two tiny synthetic requests and to earlier verification rounds; they are not successful model responses or a replacement for the unmet three-brief criterion.
